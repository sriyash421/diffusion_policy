# Candidates from subgoal — per-candidate verifier feedback

Generated by `scripts/dump_candidate_scores.py`. Every number comes from a closed-loop
rollout driven by **whatever the policy actually deploys** — the argmax candidate for
the argmax arms, the extra conditioned sample for the final-pass ones — so these are
the scores a real deployment saw.


> **Do not compare raw levels across arms.** Two effects confound them.
>
> *Different states.* Each arm is driven by its own selection rule, so the final-pass
> arms visit a different (and worse) state distribution than the argmax arms.
>
> *Episode composition.* The verifier value improves steeply WITHIN an episode — the
> block starts far from the goal and gets pushed in, so the mean candidate value runs
> about -138 px at the first control step to -22 px by step 20. A finished episode
> stops contributing steps. So the pooled mean over live steps is mostly a statement
> about *which stage of the approach* the pooled steps came from, and it moves far
> more with the mix of early-vs-late steps than with policy quality.
>
> Concretely, `subgoal-value` clean between its n=16 and n=64 dumps: success rises
> 0.55 → 0.70, yet the pooled mean *falls* 9.4 px. Succeeded episodes run ~20 control
> steps and stop; failed ones run the full 38 and so contribute many late, high-value
> steps — their mean is **-42.3** against **-51.8** for the succeeded ones. Improving
> the policy converts failed episodes into succeeded ones, which REMOVES those
> high-value late steps from the pool: the failed-episode share of live steps drops
> 61% → 45% and the pooled mean drops with it. **A lower mean here indicates a better
> policy, not a worse one.**
>
> The statistics the conclusions rest on are immune to both, because they are computed
> WITHIN a control step: step-centered means, within-step SD, record rate against the
> permutation null, the deployed sample's rank, and the prefix curves (every prefix
> is measured on the same visited states).


The verifier value is in **pixels**, ≤ 0, higher (less negative) is better. Which
value depends on the run (`pusht_verifier.VALUE_FNS`):
`t_goal` = `-mean_kp||feedback||` (0 on goal, ~-300 worst) — every run before
2026-08-19; `armT` = `-(mean_kp||feedback|| + ||agent - T_centre||)` (0 only with the
T on goal AND the arm at its centre, ~-800 worst) — runs after. The two are not
comparable; the run directory carries `ver-<value>` from the cutover onward.
Candidates are listed **in generation order** — candidate 0 has an empty search
context (the no-search baseline) and candidate k is conditioned on candidates
0..k-1 and their feedback.


## 0. The test, and how to read it

The question is whether candidate `k` is a new running maximum over `0..k-1` more
often than **order alone** would produce. If yes, conditioning on the previous
candidates is steering generation. If no, the search is resampling a fixed
distribution and the entire gain belongs to the oracle argmax.


### The obvious null is wrong here

For a continuous i.i.d. sequence that probability is exactly `1/(k+1)`. These scores
are **not** continuous: many candidates never touch the block, so the sim returns
byte-identical values, and strict-inequality records are suppressed by the ties.
Reshuffling each step's own candidates — exchangeable by construction, so it *must*
hit the null if the null applies — lands ~30% below `1/(k+1)`. Measuring against the
analytic curve therefore scores a tie artefact as evidence, and reports every arm as
**worse than resampling** when the opposite is true.


### The null used instead

**The permutation null**: the same step's candidate values, order shuffled, averaged
over 200 shuffles. It holds the value multiset (ties and all) fixed and destroys only
the ordering, which is exactly the thing under test. `excess records` sums
`(observed − permutation)` over `k ≥ 1`; **0 means order carries no information**.
The analytic `1/(k+1)` is still shown in the plots, as a dotted line, only to make
the size of the tie effect visible.

### Reward — max, last step, and discounted

PushT reward is `clip(coverage / success_threshold, 0, 1)` per step, and the env
sets `done` the instant coverage clears the threshold. Two consequences the usual
`max` metric hides:


* **No time preference.** An 8-step solve and a 38-step solve both score 1.0.
  `disc succ` below fixes that: it is `γ^(steps to success)`, 0 if never — monotone
  in both succeeding and succeeding sooner. At γ=0.99, solving 30 steps later is
  worth 26% less.
* ⚠️ **`Σ γᵗ rₜ` is backwards on this task** and is shown only as a warning. The env
  terminates the instant coverage clears the threshold, so a fast solve contributes
  FEWER reward terms than a slow one and scores LOWER — the 0.90-success arms come
  out below the 0.70-success ones on it. Episode length is endogenous here, so a
  sum over the realized horizon is not comparable across policies.
* **`max` can credit a moment the policy did not hold.** Because a success
  terminates at its peak, `last` equals `max` for every successful episode — so
  any gap between them comes entirely from FAILED episodes that brushed the goal
  and drifted off. `lost after peak` is how often that happened.

## 2. Does a higher n raise the average? — prefix statistics

`mean` is the average distance feedback over candidates `0..n-1`; `max` is the
best-of-n curve over the same prefix. The question "does the average rise with n"
is the `mean` row; the `max` row is what people usually assume that question means,
and the two diverge sharply.


**Read the `‖` as a regime change, not a trend.** `predict_n_actions` switches to a

## 3b. Which candidate slot does the argmax land on?

Scoped to **discriminating** control steps -- those where the candidates do not
all score identically. On a blind step every slot is a maximizer and `np.argmax`
returns 0 every time, so including them measures numpy's tiebreak rule rather
than the policy.


**Two columns, two different questions.** `first` is `np.argmax`, which is what
`select_candidate` uses, so it is literally the slot the deployed policy executed
-- but it is a fact about the tiebreak rule wherever candidates tie. `unique`
restricts to steps with a single maximizer and answers which slot genuinely wins.


**Compare against `perm null`, never against `uniform`.** The permutation null
reshuffles each step's own value multiset, holding the ties fixed and destroying
only the ordering -- the one thing under test. Ties are rife here, so a shuffled
sequence already departs from `(n-1)/2`.


⚠️ **The i.i.d. arms are not baselines OF this statistic -- they ARE its null
distribution**, measured on real data with the real tie structure. UNet BC discards
the search context and ST k=1 has no context capacity, so neither has any reason to
prefer a slot. If a k>1 arm sits inside their band, the search context does not move
the argmax slot.

### Search weighting (K=1)


**Slot loss weighting λ=0.0 — TRAINING ONLY.** A per-slot factor on the
loss terms (`_slot_weights`, used only by `_compute_loss`), so it has no
effect at inference: there is no loss to weight. `w_k ∝ 0.0^(K-1-k)`, normalized to mean 1:


| slot | 0 |
|---|---|
| weight | 1.00 |

⚠️ This keys the weight to the ABSOLUTE slot index, but the final pass is
conditioned on `min(n, K-1)` entries — so which conditional is *deployed*,
and how well it was trained, depends on the eval n:


| eval n | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---|---|---|---|---|---|---|---|
| slot deployed | 0 | 0 | 0 | 0 | 0 | 0 | 0 |
