## SLURM: account vs partition

They are different namespaces and the names overlap confusingly. `gpu-l40-weirdlab` is an
**account**; the **partition** is plain `gpu-l40`. Passing the account as `--partition`
fails with `invalid partition specified` — this is what stopped the first launch attempt.

- training (per user): `--account=gpu-l40-weirdlab --partition=gpu-l40`, and
  `--account=gpu-l40s-weirdlab --partition=gpu-l40s`. The launcher alternates the two.
- evals (per user): robotics A40 (`--account=gpu-a40-robotics --partition=gpu-a40`),
  ckpt (`--account=robotics --partition=ckpt`, what the eval sbatch already uses), or
  CSE (`--account=gpu-l40s-cse --partition=gpu-l40s`).
- `--time` must be finite and fit before the **2026-08-11 09:00** maintenance reservation,
  or SLURM parks the job forever with `Reserved_for_maintenance`. Launcher uses 1d for BC,
  3d for search.

## What changed to make this possible

**`n_demos` is now the single data-budget knob** (`train_pusht_diffusion_search.yaml`). It
selects the split manifest (`splits/pusht_seed42_train${n_demos}.json`) *and* appears in
`run_name`, so two budgets can never share an output directory — without this a 100-demo
relaunch would have silently resumed the old runs' checkpoints.

**BC is the same policy with `max_actions: 1`**, not a separate class. That sets the
transformer's `max_context_actions` to 0, so every candidate is drawn with an empty
context. Encoder, backbone, normalizer, optimizer, LR schedule, trainer and eval harness
are inherited unchanged, so the *only* difference from the search arms is the search.
Consequences: training is plain denoising BC and never spawns the verifier pool; n=1 eval
is an ordinary BC rollout; n>1 eval is best-of-n over i.i.d. samples, which gives BC the
same test-time budget as search and is the comparison that isolates the *learned* context.

`PushTSearchImageRunner` now calls `predict_action` when `n_search_actions == 1`, so a BC
rollout does not physics-simulate its single candidate.

**Split manifests** `pusht_seed42_train25.json` / `_train100.json`, both generated by
`scripts/dump_pusht_splits.py`. Verified: train25 ⊂ train100 (25 of 100), val and test
byte-identical, same zarr checksum. 3,325 vs 12,899 train frames.

## Correction to the premise

The user asked for BC on "the 25 demos used to train the search policy". No run was ever
trained on 25. The six existing runs (`offline/ctx-*_seed-42/`, no `demos-` in the name)
predate the manifest: `n_val_episodes: 10` and `train_ratio: 0.2` gave a 146-episode pool →
**29 train episodes**, selected against a **10-episode val split**. So they are neither the
same budget nor the same partition as anything in Round 7, and their numbers are not
directly comparable. Round 7's 25-demo arm is a real 25 on the shared partition.

**Gap worth deciding on:** there is no search arm at 25 demos, so the design is
BC{25,100} × search{100}. Adding search@25 (6 more runs) would complete a
budget × search 2×2 and is the only way to answer "does search substitute for data".

## Parity policy: BC as the baseline for search

BC must be neither gratuitously different from the search arms nor artificially handicapped.

**Shared, and staying shared** (these define the experiment; a difference confounds the one
variable under test): data and split manifest, architecture, obs encoder, horizon /
n_obs_steps / n_action_steps, noise scheduler, optimizer and LR schedule, EMA, batch size,
and the full eval protocol -- same episodes, same seeds, same success threshold.

**`num_inference_steps` stays shared at 8.** It is 8 for search because a search training
step samples `max_actions-1` candidates, and 100 would be 12.5x the dominant cost. BC
samples nothing during training, so inheriting 8 looked like a free handicap. It is not:
measured on frozen BC weights, n=1 success was identical at 8 / 16 / 32 / 100 inference
steps on two checkpoints (all 0%). Sampler quality is not the binding constraint, so parity
here costs BC nothing. Measured by `scripts/diag_bc_n1.sbatch`.

**Only training length differs.** Equal gradient steps is not neutral:

| | at 20k steps |
|---|---|
| BC | val_loss still falling -- undertrained ~60x vs upstream's 3050 epochs |
| search | already past peak -- all six legacy arms select best at step 1000-8000 of 20000 |

Holding both at one budget starves the baseline and flatters the method. Each is trained to
its own optimum (BC 300k, search 20k) and the checkpoint is selected on **val** for both, so
test stays honest. The compute asymmetry is real and must be reported alongside any result:
a BC gradient step is ~100x cheaper than a search step, so at equal wall-clock BC gets far
more steps.
